One RDF graph · four notations · one traversal

Diagrams are views. The graph is the source of truth.

Every tool that draws software draws one layer. C4 tools stop at a link to the repository. BPMN modelers never see the screen that fires a process. IFML never wired its hooks to data. SHACL lives in its own silo. SemanticSeams puts every element of every layer in one RDF graph, as a resource with an IRI, and treats each diagram as a view over it.

Zooming in is a graph traversal

Click a node and the renderer switches with the node's notation. The descent below is the canonical one, and the viewer completes it over a hand-authored model today.

  1. 01
    Open the C4 container view: the navigation shell.click client web interface
  2. 02
    Land on its IFML surface: pages, view components, events, flows.click an event's action
  3. 03
    Land on the BPMN diagram behind that action, rendered by bpmn-js from the native XML.click a business-rule task or a data object
  4. 04
    Land on the DMN decision table, or the SHACL shape of the data itself.same graph, different renderer

The seams are the product

There is no BPMN ontology here and no DMN ontology. Native XML stays native and is rendered by the stock viewers. Only the elements that participate in a cross-layer edge get an IRI, and the edges come from one small bridging ontology, built to four rules.

Few and generic beats many and precise

Twenty-five predicates. Each one must earn a cross-layer query or it does not exist.

Reuse inside layers, mint where layers meet

C4, IFML, BPMN, DMN and SHACL keep their own vocabularies. The seam ontology only names the joins.

The method applied to itself

SHACL shapes constrain the seams. CI parses every file, validates the examples, proves the shapes reject bad seams, and checks every predicate is exercised.

Questions no single-notation tool can answer

Because everything is one graph, cross-layer questions are SPARQL. Three ship as canned queries with exact expected rows asserted in CI, and they are buttons on the viewer's inspector, not SPARQL a user sees.

Which UI events can eventually write to this data shape, and through which task?

what-writes-shape.rq · compliance and security review

What breaks, containers and processes both, if this deployment node goes away?

impact-of-node.rq · impact analysis and drift

Which process tasks may move an entity out of this state?

what-moves-state.rq · lifecycle audit

The first one, as it ships in docs/queries/what-writes-shape.rq: a property path from an IFML event through the seams to whatever writes the shape, including the async hop through a channel.

SELECT DISTINCT ?event ?writer WHERE {
  ?event a ifml:Event .
  ?event ( (seam:triggers/seam:detailedBy/^seam:inModel)
         | seam:decidedBy
         | seam:invokes
         | (seam:publishesTo/^seam:subscribesTo/seam:inModel/^seam:inModel)
         )+ ?writer .
  ?writer seam:writes ?shape .
}

Where it is

Concept and proof of concept, July to September 2026. The pieces below exist and are under test; editing, SHACL-driven forms, IFML to htmx generation and deployment generation come after.

1
