# Research note: SysML v2, read against the graph

*Status: proposal, 2026-11-02. Not yet scheduled. Linked from the
[backlog](../backlog.md) ("Not yet scheduled" section, items W1 to W5). Takes up the
"Where SysML v2 points the same way" section of the
[UML coverage note](2026-10-29-uml-coverage-and-gaps.md) and follows the
[domain-driven design note](2026-11-02-domain-driven-design.md), which used the same
method. Written against `main` at `50cddfa`.*

## The questions

1. Does SysML v2 offer diagrams a user of SemanticSeams should author, the way they
   author BPMN, DMN, IFML and shapes?
2. Can SysML v2 be generated from the model, the way `seams sequence` derives UML
   sequence diagrams?
3. Does SysML v2 cover ground in application generation that the project has not
   thought about?

## Short answer

- **No diagrams to author.** SysML v2 has no diagram types in the UML sense. It has
  eight standard *view definitions*, each a query over one model plus a rendering,
  which is this project's "diagrams are views" stated by a standards body. The five
  graph-shaped ones are already covered by the C4, IFML, BPMN and statechart renderers
  and the derived sequence diagram. Authoring them here would restate facts the graph
  holds, the drift the UML note refused (section 2).
- **Three kinds of fact are worth taking, not diagrams.** Requirements with
  satisfaction and verification links, concerns and stakeholders, and variability.
  Requirements are the gap the UML note already named; SysML v2 gives it a tested
  shape, and the `verify:` vocabulary is its verification half without the
  requirement to point at (sections 2.2 and 4.1).
- **Yes, export it, and it is worth more than Mermaid.** The textual notation is a
  whole-system language, so one generated `.sysml` file covers every layer, opens in
  SysON and Syside, and diffs in a pull request. Architecture, data, lifecycles,
  contracts, requirements and scenarios map cleanly; BPMN and DMN export lossily;
  IFML has no counterpart. As with the sequence deriver, every gap the exporter
  reports is a model audit (section 3).
- **Coverage not thought about:** requirements and concerns, allocation as one
  explicit relationship, variation points, individuals and snapshots for the
  as-deployed and as-executed graphs, parametric constraints for non-functional
  budgets, and an API whose projects, commits, branches and queries are prior art for
  the write path and a model API (section 4).
- **Do not lift the metamodel, and do not wait for an RDF standard.** KerML into
  RDF is the BPMN-ontology swamp again, and the OMG publishes no RDF vocabulary; the
  mappings that exist are community work with an open-world caveat (section 5).

## 1. SysML v2 in November 2026

Facts checked against the OMG specification pages and the release repository on the
date of this note.

| Item | State |
|---|---|
| Specifications | SysML 2.0, KerML 1.0 and the Systems Modeling API and Services 1.0, adopted by the OMG in July 2025 and published as formal specifications in September 2025 (`formal/26-03-01` to `formal/26-03-03`), editorially updated in March 2026 for ISO submission. Beta 2 of SysML 2.1, KerML 1.1 and API 1.1 shipped in the August 2026 release |
| Normative artifacts | MOF XMI of the abstract syntax, a JSON schema of the abstract syntax, and the libraries as KPAR archives. No RDF, OWL or Turtle vocabulary is listed |
| Notations | A textual notation (the primary one; every example and library is textual) and a graphical notation, both over one abstract syntax. The textual notation is what tools exchange |
| Views | Eight standard view definitions in the Systems Library: General, Interconnection, Action Flow, State Transition, Sequence, Geometry, Grid and Browser. A view is a view definition plus `expose` relationships and filters, rendered by a rendering definition |
| API | REST over projects, commits, branches, tags, elements and queries. Branching gives multiple commit histories; elements are versioned per commit |
| Open-source tools | SysON (Eclipse, Obeo and CEA; web-based graphical modeler; 2026.9 is current; eight-week cadence; the 2026.7 and 2026.9 releases added expression editing, requirement derivation and framing of concerns), Syside by Sensmetry (textual, VS Code; a free Community Edition and a licensed Pro edition), the OMG pilot implementation with a Jupyter kernel, and the API and Services reference implementation |
| RDF | The OMG chose SMOF so that a mapping to OWL 2 DL would be possible; none is published as a normative artifact. openCAESAR's `sysml-adapter` converts the textual notation to OML and OWL in both directions as community work; an ESA question-and-answer record states that no executable standard transformation exists and that the open-world and closed-world mismatch is left to the user. Ordered multiplicities need reification in plain RDF |

Two facts matter most for this note. The language is textual first, which makes it an
export target like Mermaid or Structurizr DSL. And views are model elements, which
makes the standard's own answer to "which diagrams" the same as ours.

## 2. Views, not diagrams

### 2.1 The eight standard views against the renderers

| SysML v2 view | What it shows | Here |
|---|---|---|
| General | Any exposed elements as nodes and edges | The node-link card renderer (ADR-0008) |
| Interconnection | Parts as nodes, connections and interfaces as edges | The C4 renderer: `arch:contains` nesting, `seam:exposes` and `seam:consumes` edges |
| Action Flow | Actions, flows, control nodes, send and accept | bpmn-js over the native XML (ADR-0007) |
| State Transition | States, transitions, triggers, guards, actions | The statechart renderer over `state:` |
| Sequence | Event occurrences on lifelines, time-ordered | `seams sequence`, derived (U1, U4) |
| Geometry | Spatial items in two or three dimensions | Not applicable |
| Grid | Elements and relationships in a table | The query catalog's rows in the inspector; a requirements table (section 2.2) |
| Browser | The membership tree | Layer mode (`GET /layers`) and `seam:inModel`; the viewer has no membership tree, and the C4 descent is its browser |

Nothing in the left column is a notation a person draws from scratch. A SysML v2 view
definition says which elements it exposes and which rendering applies; the tool draws
it. That is the query catalog in `docs/queries/` bound to a renderer, which the UML
note already observed. The two ideas worth borrowing are terms, not diagrams:

- **`expose` with a filter** is a saved query that names its focus and its element
  types. The catalog's canned queries leave the focus node free and bind it in the
  viewer; a SysML view usage binds it in the model. Letting a model carry its own
  saved views, as `seam:Model`s of a `seam:View` notation whose payload is a query
  name and a focus, is a small step the viewer's buttons already prepare for.
- **Rendering definitions** separate what a view exposes from how it is drawn. The
  viewer dispatches on `seam:notation` today, which couples the two. Keeping them
  coupled is right while every notation has one renderer; the SysML split is the
  shape to take when a second rendering of the same facts appears, such as Mermaid
  and an interactive canvas for the same sequence.

So the answer to the first question is no for diagrams. SysML v2 does not add a
notation a user should author here, and SysML v1's own history, the fourteen-diagram
menu that let diagrams disagree, is the warning the outline already quotes.

### 2.2 What a user would author: requirements

What SysML v2 has that the graph lacks is not a view but three kinds of fact, and the
first is the one the UML note's section 3.1 called the biggest gap: there is nowhere
to say why an element exists or how anyone knows it works.

SysML v2 models a requirement as a constraint with a subject and text, in a definition
and usage pair, and links it with four relationships: `satisfy` (an element claims to
meet it), `verify` (a verification case checks it and returns a verdict of pass, fail,
inconclusive or error), `derive` (a requirement refines another), and `frame` (a
requirement addresses a concern a stakeholder holds). Everything in that sentence
except the verdict is a graph edge, and the verdict is what the `tests` generator
already produces.

A thin vocabulary in that shape, `req:` beside `verify:`:

| Term | Meaning | Reuses |
|---|---|---|
| `req:Requirement` | A statement with `rdfs:label`, text and a subject | The subject is any element, usually a shape or a process |
| `req:satisfiedBy` | Requirement to the elements that claim to meet it | Any element; a seam, so it lives in the seams graph |
| `req:verifiedBy` | Requirement to a `verify:Scenario`, `verify:DecisionExample` or shape example that checks it | The existing `verify:` terms are the verification cases |
| `req:derivedFrom` | Requirement to the requirement it refines | |
| `req:Concern`, `req:frames` | A stakeholder's concern and the requirements that address it | `odrl:Party` as the stakeholder |

Every term earns a query the enterprise persona asks today and nothing can answer:
which requirements have no verifying scenario, which elements satisfy no requirement
(dead model, from the other side), which requirements a breaking shape change (U8)
touches, and which concerns a release leaves unaddressed. The requirements table is
SysML's Grid view over these facts, and a derived "requirements and verification"
picture is the UML note's use-case projection with the goal filled in.

SHACL constraints are requirements on data already. A `req:Requirement` whose subject
is a shape and whose `req:satisfiedBy` is a property shape makes that explicit without
duplicating the constraint. The ADR for W2 should decide whether a property shape can
be the subject or only the satisfier.

The other two kinds of fact, variability and parametric constraints, are in section 4.

## 3. Exporting SysML v2 from the model

### 3.1 The mapping, layer by layer

The textual notation covers the whole system, so one generated package can hold every
layer. The mapping, with what is lost:

| Layer | SysML v2 construct | Fidelity |
|---|---|---|
| `arch:System`, `arch:Container`, `arch:Component`, `arch:contains` | `part def` and nested `part` usages | Clean |
| `arch:DeploymentNode`, `arch:Environment`, `seam:deployedTo`, `deploy:override` | `part` usages for nodes; `allocate` container to node; one `variation` with a `variant` per environment (ADR-0015) | Clean; environments are the one variability the model has |
| `hydra:Operation`, `comm:Channel`, `seam:exposes`, `seam:consumes` | `port def` per endpoint with `in` and `out` items; `interface def` and `connect` for each consume | Clean for the topology; `comm:path` and `hydra:method` become `attribute`s |
| `seam:acceptsShape`, `seam:returnsShape`, `seam:mediaKind` | Item types on the port's items; `metadata` for the media kind | Clean |
| `sh:NodeShape`, property shapes | `item def` with `attribute`s typed from `ScalarValues`; `sh:node` as a nested item; `sh:minCount`/`sh:maxCount` as multiplicity; `sh:in` as an `enum def` | Clean for structure; value constraints (`sh:minInclusive`, `sh:pattern`) become `constraint` usages or are reported as gaps |
| `state:StateMachine`, `seam:lifecycle` | `state def` with `transition first ... then ...`; `exhibit state` on the item's part | Clean; `state:trigger` labels become `accept` triggers |
| `proc:Process` and its BPMN | `action def` with nested `action`s and `succession`s read from the sequence flows, as `seams sequence` reads them; exclusive gateways as `decide` nodes; user tasks as actions with the party as `actor` | Lossy: lanes, timers, boundary events beyond `seam:catches`, and message semantics are approximated |
| `dec:Decision` and its DMN | `calc def` with the bindings as parameters | Lossy: the table itself is not expressible; export the `verify:DecisionExample`s as the calc's verification cases instead |
| `seam:fires`, `seam:writes`, `seam:reads`, `seam:invokes`, `seam:decidedBy` | `flow` and `succession` inside the action, `allocate` where the seam says where something runs | Mostly clean |
| `odrl:Policy`, `seam:governedBy` | `requirement` usages with the party as `actor`, or `metadata` | Lossy: ODRL has no SysML counterpart; a `metadata def` keeps the IRIs |
| `verify:Scenario`, `verify:DecisionExample`, shape examples | `verification def` and usages with an `objective`; the given values as attribute bindings; the expected state as the verdict condition | Clean, and the clearest win: SysML tools render them |
| `seam:executes`, `seam:storedIn`, `seam:implementedBy` | `allocate` | Clean |
| IFML | No counterpart. A page as a `part` with ports for its events is the nearest, and it is a stretch | Gap, reported |
| `docs/queries/*.rq` | `view def` with `expose` and a `filter`, rendered by the standard view that fits | Clean for the catalog's structure; the SPARQL text is kept as `doc` |

A sketch of the expense tutorial's chapter 9 in the textual notation, hand-written
from the graph and not yet run through the pilot implementation, to show the shape of
the output:

```sysml
package 'Expense Approval' {
    import ScalarValues::*;

    item def Expense {
        attribute description : String;
        attribute amount : Rational;
        attribute date : String;
    }

    state def ExpenseLifecycle {
        entry; then draft;
        state draft; state submitted; state approved; state rejected; state paid;
        transition submit  first draft     then submitted;
        transition approve first submitted then approved;
        transition reject  first submitted then rejected;
        transition pay     first approved  then paid;
    }

    port def ExpenseApi { in item submitExpense : Expense; }

    part def ExpenseSystem {
        part employeePortal;
        part expenseApi { port api : ExpenseApi; }
        part expenseDb;
        connect employeePortal to expenseApi.api;
        allocate expenseApi to app01;
    }

    requirement def AutoApproveSmallExpenses {
        subject expense : Expense;
        doc /* An expense under the routing threshold is approved without a manager. */
    }

    verification def AutoApproved {
        objective { verify AutoApproveSmallExpenses; }
    }
}
```

The requirement block is the one thing in the sketch the graph cannot supply today;
everything else is a seam or a layer fact.

### 3.2 How it would be built

A `sysml` generator under the generator protocol
([ADR-0016](../adr/0016-generator-protocol.md)): `extract` walks the `seams` views
into a frozen view model, `render` writes one `<system>.sysml` with a header naming
the model hash, sorted everywhere, byte for byte against a golden for the chat app and
chapter 9, with a trace sidecar ([ADR-0019](../adr/0019-generation-trace.md)) like any
other output. Gaps are reported the way `seams sequence` reports them, as `//` comment
lines in the output and on stderr, never dropped. Listed in `seams.toml` like the
other generators, so `seams check` reports a stale export.

The export is also the audit the UML note described: every construct the exporter
cannot fill from the graph is either a missing fact or behaviour that bypasses it. The
first run will find the same two facts the sequence deriver found, and likely the
requirement gap above.

### 3.3 Import: no, with one exception

A SysML v2 model authored in SysON restates facts the graph holds, and importing it
would create the second source of truth the project refuses. The exception is the
enterprise persona's entry point, which the UML note already lists as a non-goal for
v1 beside OpenAPI, SQL DDL and compose: an existing SysML v2 model of the system's
structure (parts, ports, connections, states, items) can seed a model's architecture,
data and lifecycle layers once. That is an import like any other, lossy by design,
after v1.

## 4. Coverage the project has not thought about

### 4.1 Requirements, concerns and stakeholders

Section 2.2. SysML v2 also gives the verification side a vocabulary the `verify:`
terms lack: a verification case has an `objective` that names what it verifies, and
returns a typed verdict. The `tests` generator produces the verdict today; `req:`
gives it something to verify.

### 4.2 Allocation as one relationship

SysML v2 has one relationship, `allocate`, for "this logical thing is realised by
that physical thing": function to component, component to node, item to store. The
graph has four seams for it: `seam:executes`, `seam:deployedTo`, `seam:storedIn` and
`seam:implementedBy`. Nothing is missing, and the four precise seams are the right
design under the "few and generic" rule only because each earns its own query. What
SysML adds is the *allocation matrix*, a Grid view of every allocation, which is one
query over those four predicates and a cheap viewer table.

### 4.3 Variability

`variation` and `variant` let one model hold a product line: a part, action or
attribute with named alternatives, and a configuration that picks one of each.
ADR-0015's environments are one such variation point, with one variant per
environment. Nothing else in the graph varies: a screen offered only to one tier, a
process branch that exists only in one deployment, a feature flag. That is a real gap
for a product with editions, and it is not one the examples need. It belongs in the
backlog as a question with a dogfood model to motivate it, not as vocabulary now.

### 4.4 Individuals, snapshots and timeslices

SysML v2 separates a definition from an *individual* (one specific vehicle), and an
individual from its *snapshots* (its state at an instant) and *timeslices* (over an
interval). The project has three graphs that are exactly this: as-designed, the model;
as-deployed, planned in ADR-0001 and fed by monitoring; as-executed, the worker's
trace rows that `seams sequence --trace` reads (U4). The terms are worth borrowing
when the as-observed named graph (UML note, section 3.5) gets its vocabulary: a trace
row is a snapshot of an individual process instance, and conformance checking is
comparing snapshots with the definition.

### 4.5 Parametric constraints

A `constraint def` with parameters, bound to attributes with `calc` usages, is how
SysML models "the latency of this flow is under 200 ms" or "the sum of these budgets
is the total". The outline lists SLOs and latency budgets as an annotation vocabulary
and nothing ships. SHACL expresses the same over data, and `sh:sparql` over the model
graph can express it over the model, once the quantities are facts. This is the
same shape as DDD's cross-aggregate invariants in the previous note: express it in
SHACL at warning severity, and let observed values from traces feed it.

### 4.6 Quantities, units and attribute definitions

SysML v2 ships a quantities and units library and models every attribute against it.
The data-centric note reached the same place through gist's magnitudes (O2). No new
work; the two agree.

### 4.7 The API as prior art for the write path and a model API

The Systems Modeling API's shape, projects that hold commits on branches, elements
addressed per commit, and queries as first-class resources, is a reference for two
planned pieces: the write path, where ADR-0017's patches are commits, and a model API
over HTTP for agents and other tools, where the catalog's queries become resources and
HTTP QUERY is the read method. SemPKM's event graphs (O4) are the same shape again.
Nothing to adopt wholesale, since the API is bound to the KerML abstract syntax, but
"shaped like the SysML v2 API" is the right description of what to build, as the UML
note said.

### 4.8 The v1-to-v2 transformation as a migration pattern

SysML 2.0 Part 2 is a normative transformation model from SysML v1 to v2. K6 plans
vocabulary versions with SPARQL Update migrations per step. A transformation
specification that is itself a model, tested on example inputs, is the pattern K6's
migrations should follow, and the Part 2 document shows how to write one.

## 5. What not to do

- **Do not add SysML v2 as an authored notation.** Its five graph views are covered,
  and a user drawing them would restate the graph.
- **Do not lift KerML or the SysML abstract syntax into RDF.** The README's reasoning
  on BPMN ontologies applies: full metamodel lifts buy nothing for navigation.
  Borrow the terms (requirement, satisfy, verify, allocate, variation, snapshot)
  where a query needs them, in the project's own thin vocabularies.
- **Do not wait for an OMG RDF mapping.** None is normative, the community ones carry
  an open-world caveat and an ordering caveat, and the export in section 3 needs
  neither: it writes the textual notation from the graph.
- **Do not generate code from SysML v2.** The direction is the other way. The graph is
  the source; SysML v2 is a view of it for people and tools that speak it.

with its ADR. W4 and W5 wait for the work they build on.

## Open questions

- **Which SysML v2 parser checks the export in CI?** The pilot implementation is Java
  and Eclipse-based; Syside's Community Edition is a VS Code extension with a language
  server; SysON has a REST API. A test that parses the golden needs one of them
  installed, which the environment does not have today.
- **One package or one per bounded context?** The DDD note's B1 makes a bounded
  context the owner of a namespace. A SysML package per context, importing the shared
  kernel, is the natural export once B1 exists; until then, one package per model.
- **Property shapes as requirement subjects or satisfiers.** Section 2.2.
- **Variability.** Section 4.3: wait for a model that needs it, and record the SysML
  terms as the candidate shape when it comes.
